### 1.（单选）以下哪一项最准确地描述了 Workflow 和 Agent 的区别？

- A. Agent 使用更大、更强的模型
- B. Agent 可以调用工具，Workflow 不可以
- C. Workflow 的流程由代码预先写好，Agent 的流程由模型在运行时决定
- D. Agent 必须由多个模型协作完成

<details>
<summary>答案</summary>

**C。** 区别在于控制流由谁决定。B 错：Workflow 同样可以调用工具，只是"什么时候调用哪个"是代码写死的。A、D 都和定义无关。（README 1.1、1.2）
</details>

### 2.（单选）下面哪个需求**最不适合**用 Agent 实现？

- A. 排查每个用户各不相同的网络故障
- B. 每月按固定公式计算员工个税
- C. 根据用户的描述，在多个系统里查找相关工单和文档
- D. 调研一个陌生的技术领域并写一份总结

<details>
<summary>答案</summary>

**B。** 个税计算是确定性的：步骤固定、结果必须精确、可以用代码百分之百正确地实现。让模型来算只会引入不确定性和成本。A、C、D 的步骤数都无法提前确定，是 Agent 的典型场景。（README 1.3）
</details>

### 3.（多选）以下哪些是企业级 Agent 必须具备、而 Demo 常常缺失的能力？

- A. 步数和预算上限
- B. 更长、更详细的 system prompt
- C. 高风险操作的人工审批
- D. 审计日志
- E. 检查点与断点恢复

<details>
<summary>答案</summary>

**A、C、D、E。** B 不是一种"能力"：提示词写得再长，也不能替代代码层面的限额、权限和记录。尤其要记住，**提示词不是安全边界**。（README 1.4、第 6 节）
</details>

### 4.（计算）一个 Agent 每一步正确的概率是 90%，一个需要 8 步的任务全部正确的概率大约是多少？这对设计意味着什么？

<details>
<summary>答案</summary>

0.9⁸ ≈ **43%**。错误会复利累积。设计上的含义：

- 减少不必要的步数（设计好的工具、能 Workflow 化的部分就 Workflow 化）；
- 每一步都要有校验和纠错机会（错误即观察，第 03 课）；
- 关键步骤加人工确认；
- 用评估度量**端到端**成功率，而不只是看单步质量（第 11 课）。
</details>

### 5.（单选）Demo 场景 3 中，`InputGuard` 拦截了"忽略之前的所有指令……"。下面哪个说法正确？

- A. 有了 `InputGuard`，就不再需要权限控制和人工审批
- B. 正则检测一定会漏掉换了说法的攻击，真正的底线是最小权限和人工审批
- C. `InputGuard` 会先调用模型判断输入是否为注入
- D. 被拦截的请求仍然会产生模型调用费用

<details>
<summary>答案</summary>

**B。** 输入检测成本低、能拦住明显的攻击，但一定会漏。真正的底线是：即使模型被骗，它也只能访问本人数据（ctx 身份）、看不到无权使用的工具（RBAC）、做不了高风险操作（人工审批）。C、D 错：Demo 中被拦截的请求模型调用次数为 0、花费为 0。（README 第 3 节，第 09 课详讲）
</details>

### 6.（简答）Demo 场景 2 中，为什么审批不是"程序阻塞等待审批人点击"，而是"暂停 → 写检查点 → 之后由另一个实例恢复"？

<details>
<summary>答案</summary>

- 审批人可能几分钟后、也可能第二天才处理，阻塞等待会长期占用进程和连接；
- 期间服务可能重启、滚动发布、扩缩容，内存里的状态会丢失；
- 把完整状态（消息历史、待审批的调用、用量）写入检查点后，任何一个实例都可以用 `run_id` 恢复，从断点继续，而不是从头再问一遍模型（既省钱，又避免模型做出不同的决定）。

这就是"持久化执行"（durable execution）的思路，第 08 课详讲。
</details>

### 7.（单选）关于多 Agent 系统，以下哪项与 Anthropic 公开分享的经验一致？

- A. 多 Agent 总是比单 Agent 效果更好
- B. 多 Agent 系统的 token 消耗大约是普通聊天的 15 倍，更适合可高度并行、信息量超出单个上下文的任务
- C. 多 Agent 可以显著降低成本
- D. 需要所有 Agent 共享大量上下文的任务最适合多 Agent

<details>
<summary>答案</summary>

**B。** 出自 Anthropic 的 [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)：Agent 约为聊天的 4 倍 token，多 Agent 约 15 倍；需要共享同一上下文或 Agent 间依赖很多的领域目前并不适合多 Agent（所以 D 恰好说反了）。（README 1.2）
</details>

### 8.（简答）什么是"致命三要素"（lethal trifecta）？Demo 里的 ITBuddy 具备其中哪几个？

<details>
<summary>答案</summary>

三要素：① 能访问私有数据；② 会接触不可信内容；③ 能对外通信。三者同时具备时，攻击者可以通过注入让 Agent 把私有数据发出去。

ITBuddy 具备 ①（员工工单、联系方式）和 ②（知识库文章可能被投毒，场景 1 就演示了）。它目前没有"发邮件、访问外部 URL"之类的对外通信工具 —— 如果将来要加，必须配合人工审批和严格的目标白名单。（README 第 5 节）
</details>

### 9.（简答）在 Moffatt v. Air Canada 案中，航空公司辩称不应为聊天机器人的错误信息负责，但没有被仲裁庭接受。对企业级 Agent 设计有哪些启示？至少写 2 条。

<details>
<summary>答案</summary>

参考要点（言之有理即可）：

- Agent 的回答代表公司，企业要为它说的话负责；
- 涉及政策、价格、法律条款的回答必须基于权威来源（通过工具检索官方政策），而不是模型的记忆，不确定时要说"不确定"或转人工；
- 要有评估集覆盖这类高风险问题，持续回归测试（第 11 课）；
- 保留完整的追踪和审计记录，出现争议时能还原 Agent 当时看到了什么、说了什么（第 09、10 课）。
</details>

### 11.（单选）课程第二部分（05–13）的讲法和第一部分有什么不同？

- A. 第二部分不写代码，只讲概念
- B. 第二部分以真实的企业问题为主线，对比多种方案的代价，给出怎么选的依据，再用代码实现其中一种
- C. 第二部分只介绍一种业界标准做法
- D. 第二部分讲的是如何换用更强的模型

<details>
<summary>答案</summary>

**B。** 第一部分"学会怎么造"：概念 → 从零实现 → 练习。第二部分"学会怎么选"：企业里的问题（限流、并发写、越权检索、灰度发布……）大多没有唯一正确答案，需要在规模、一致性、成本、团队能力之间取舍，所以每节课由若干张"问题卡片"组成：场景 → 多方案对比 → 怎么选 → 本课实现。（README 1.6）
</details>

### 12.（简答）ITBuddy 上线后，同一个员工在网页和企业 IM 里几乎同时给它发了两条消息，两个请求被两台服务器分别处理，都读到了同一份会话历史、各自追加后写回。会出什么问题？你能想到哪几类解决思路？

<details>
<summary>答案</summary>

问题：后写回的一方会覆盖先写回的一方（丢失更新），会话历史里少了一轮对话；如果两轮都触发了写操作，还可能重复执行。

解决思路（第 13 课会逐一对比它们的代价和适用场景，这里能说出大方向即可）：

- **悲观锁**：处理某个会话前先加锁，同一时刻只有一个请求能处理它；
- **乐观锁**：写回时带版本号，版本不一致就拒绝写入、重新读取后重试；
- **分区串行化**：按会话 ID 把请求路由到同一个队列分区或同一个 Worker，天然排队执行。

没有哪一种永远最好：冲突频率、延迟要求和已有的基础设施决定了选哪一个 —— 这正是第二部分要训练的判断力。
</details>
