# Glossary (English–Chinese)

> 📖 Part of the "domain reference handbook". Terms are grouped by topic rather than alphabetically, because related terms are easier to connect when you read them together.
> Related docs: [Cheatsheet](cheatsheet.en.md) · [Framework comparison](framework-comparison.en.md) · [Failure-mode catalog](failure-modes.en.md)

**How to use it**: each term gets a one-sentence plain-language explanation. Names in `code font` are the matching agentkit classes or functions, so you can look them up in the source. The Chinese column gives the term used in the Chinese lessons and code comments. Stuck on a word? `Ctrl+F` works for both English and Chinese.

**278** terms in 15 groups, plus 34 commonly confused pairs.

## 1. Core Concepts

| English | Chinese | In plain words | Lesson |
|---|---|---|---|
| Agent | 智能体 | A program where the model decides, in a loop, which tools to call and how many times, until it thinks the task is done. `Agent` | [Lesson 02](../lessons/02_agent_loop/README.en.md) |
| Workflow | 工作流 | A program whose steps and order are hard-coded, with the model handling only some of the steps. More predictable, cheaper, and easier to test than an agent. | [Lesson 06](../lessons/06_orchestration/README.en.md) |
| Agent Loop | Agent 循环 | The "call the model → run the tools it asked for → feed the results back → call the model again" loop. It is the heart of every agent. | [Lesson 02](../lessons/02_agent_loop/README.en.md) |
| Augmented LLM | 增强型 LLM | A model call equipped with retrieval, tools, and memory; the basic building block of workflows and agents (the term comes from Anthropic's "Building Effective Agents"). | [Lesson 06](../lessons/06_orchestration/README.en.md) |
| System Prompt | 系统提示词 | The "job description" the model gets at the start of every conversation, defining who it is and how it should behave. Assume users can extract it. | [Lesson 02](../lessons/02_agent_loop/README.en.md) |
| Token | 词元 | The smallest unit of text a model processes; billing and context length are both measured in tokens. In Chinese, one character is roughly one token (varies by model). `estimate_tokens` | [Lesson 01](../lessons/01_llm_essentials/README.en.md) |
| Context Window | 上下文窗口 | The maximum number of tokens the model can "see" at once, including the system prompt, history, tool definitions, and tool results. | [Lesson 01](../lessons/01_llm_essentials/README.en.md) · [Lesson 04](../lessons/04_context_memory/README.en.md) |
| Tool Calling / Function Calling | 工具调用 / 函数调用 | Instead of answering directly, the model outputs a structured request ("call this function with these arguments") that your program executes. | [Lesson 01](../lessons/01_llm_essentials/README.en.md) · [Lesson 02](../lessons/02_agent_loop/README.en.md) |
| ReAct (Reasoning + Acting) | ReAct | A paradigm where the model alternates between "thinking" and "acting" (calling tools). It comes from Yao et al.'s 2022 paper and is the intellectual origin of the modern agent loop, as well as the most basic single-agent architecture. | [Lesson 05](../lessons/05_agent_architectures/README.en.md) · [Lesson 02](../lessons/02_agent_loop/README.en.md) |
| Max Steps / Max Turns | 步数上限 | The maximum number of model-call rounds allowed in one run; the last hard line of defense against runaway loops burning money. `Agent(max_steps=...)` | [Lesson 02](../lessons/02_agent_loop/README.en.md) |
| Stop Reason / Finish Reason | 结束原因 | Why a run or a model call ended: it answered, hit a limit, got blocked, is awaiting approval, and so on. One of the most important monitoring dimensions. `RunResult.stop_reason` | [Lesson 02](../lessons/02_agent_loop/README.en.md) |
| Non-determinism | 非确定性 | The same input can produce different outputs and take different steps, so "it worked once" doesn't mean it works. | [Lesson 01](../lessons/01_llm_essentials/README.en.md) · [Lesson 11](../lessons/11_evals/README.en.md) |
| Temperature | 温度 | A sampling parameter that controls output randomness. Lower is more stable, but even 0 doesn't guarantee full reproducibility. | [Lesson 01](../lessons/01_llm_essentials/README.en.md) |
| Streaming | 流式输出 | The model returns output as it generates it, so users don't wait for the whole response. Crucial to the experience on long tasks. | [Lesson 01](../lessons/01_llm_essentials/README.en.md) · [Lesson 14](../lessons/14_cost_latency/README.en.md) · [Lesson 30](../lessons/30_async_runtime/README.en.md) |
| Reasoning Model | 推理模型 | A model that generates internal "thinking" before it answers. Thinking tokens are billed as output and take up context, so use it for planning and hard problems, not simple classification or latency-sensitive steps. | [Lesson 01](../lessons/01_llm_essentials/README.en.md) |
| Hallucination | 幻觉 | The model states something false, fluently and confidently. Get facts from tools and retrieval, and judge what the agent actually did from its tool-execution records, never from its text. | [Lesson 01](../lessons/01_llm_essentials/README.en.md) |
| Test Double / Scripted LLM | 测试替身（剧本模型） | A "fake model" that returns results from a pre-written script, making agent tests zero-cost and reproducible. `ScriptedLLM` | [Lesson 02](../lessons/02_agent_loop/README.en.md) |
| LLM Abstraction | 模型抽象层 | Business code depends on one small `chat()` interface instead of a vendor SDK, which makes it easy to swap models and layer on capabilities. `LLM` protocol | [Lesson 02](../lessons/02_agent_loop/README.en.md) |

## 2. Tools

| English | Chinese | In plain words | Lesson |
|---|---|---|---|
| Tool | 工具 | The agent's only channel to the outside world: query a database, call an API, send an email. Essentially a function that comes with a manual. `@tool` | [Lesson 03](../lessons/03_tools/README.en.md) |
| Tool Description | 工具描述 | The tool's manual, written for the model: what it does, when to use it, and when not to. The model picks tools based entirely on it. | [Lesson 03](../lessons/03_tools/README.en.md) |
| JSON Schema | JSON Schema | The standard format for describing what arguments look like: which fields exist, their types, which are required, and the allowed values. | [Lesson 03](../lessons/03_tools/README.en.md) |
| Argument Validation | 参数校验 | Checking that the model's arguments are valid before running the tool. Model-supplied arguments are just generated text and must be treated as untrusted input. | [Lesson 03](../lessons/03_tools/README.en.md) |
| Errors as Observations | 错误即观察 | When a tool fails, don't crash the agent with an exception. Turn the error into text the model can understand and feed it back so the model can correct itself. `ToolResult` | [Lesson 03](../lessons/03_tools/README.en.md) |
| Risk Tiering | 风险分级 | Labeling every tool read / write / dangerous; permissions and approvals use the tier to decide whether to allow a call. `Tool(risk=...)` | [Lesson 03](../lessons/03_tools/README.en.md) |
| Idempotency | 幂等 | Running an operation once or many times has the same effect. Retries and crash recovery depend on it; without it you get double charges and duplicate tickets. | [Lesson 08](../lessons/08_reliability/README.en.md) |
| Idempotency Key | 幂等键 | A unique key that identifies "this is the same operation", used to deduplicate replays. agentkit uses `run_id:call_id`. `ToolContext.idempotency_key` | [Lesson 08](../lessons/08_reliability/README.en.md) · [Lesson 26](../lessons/26_state_and_queues/README.en.md) |
| Trusted Context | 可信上下文 | Information the system (not the model) injects into tools, such as user ID, tenant ID, and roles. The model can neither see nor change it. `ToolContext` | [Lesson 03](../lessons/03_tools/README.en.md) |
| Output Truncation | 输出截断 | When a tool returns too much, keep only the first N characters and tell the model the output was truncated, so it doesn't blow up the context. `Tool(max_output_chars=...)` | [Lesson 03](../lessons/03_tools/README.en.md) |
| ACI (Agent-Computer Interface) | Agent-计算机接口 | By analogy with HCI (human-computer interaction): a tool's name, parameters, description, and return format are the agent's user interface, and they deserve the same design care. | [Lesson 03](../lessons/03_tools/README.en.md) · [Lesson 24](../lessons/24_coding_agents/README.en.md) |
| Poka-yoke | 防呆设计 | A manufacturing idea: design things so mistakes are impossible. Applied to tools, it means reshaping parameters so the model is less likely to misuse them. | [Lesson 03](../lessons/03_tools/README.en.md) |
| Structured Output | 结构化输出 | Making the model output JSON that conforms to a given schema, instead of free text, so downstream code can rely on it. `complete_json` | [Lesson 01](../lessons/01_llm_essentials/README.en.md) · [Lesson 06](../lessons/06_orchestration/README.en.md) |
| MCP (Model Context Protocol) | 模型上下文协议 | An open protocol that connects AI applications to external tools and data sources, a kind of "USB port for AI". Servers can provide tools, resources, and prompt templates. | [Lesson 03](../lessons/03_tools/README.en.md) · [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |
| Sandbox | 沙箱 | An isolated execution environment (container, VM, etc.), so untrusted code or risky tools can't affect anything outside it when they misbehave. | [Lesson 03](../lessons/03_tools/README.en.md) · [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |
| Tool Poisoning | 工具投毒 | Hiding malicious instructions in a tool description. Because descriptions enter the model's context, this amounts to injecting content into the prompt. | [Lesson 09](../lessons/09_security/README.en.md) · [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |

## 3. Context and Memory

| English | Chinese | In plain words | Lesson |
|---|---|---|---|
| Context Engineering | 上下文工程 | The whole practice of deciding what the model sees on each call: what to include, what to drop, what to compress, and when to retrieve. | [Lesson 04](../lessons/04_context_memory/README.en.md) |
| Short-term Memory | 短期记忆 | The message history of the current conversation. It's gone when the session ends. | [Lesson 04](../lessons/04_context_memory/README.en.md) |
| Long-term Memory | 长期记忆 | Information stored externally and kept across sessions (e.g., user preferences), retrieved into the context when needed. `MemoryStore` | [Lesson 04](../lessons/04_context_memory/README.en.md) · [Lesson 18](../lessons/18_memory_systems/README.en.md) |
| Sliding Window | 滑动窗口 | When the context gets too long, keep only the most recent messages. Simple and cheap, but early information is lost. `SlidingWindow` | [Lesson 04](../lessons/04_context_memory/README.en.md) |
| Compaction / Summarization | 压缩 / 摘要 | Having the model summarize the older part of a conversation and replacing the original to save context. The cost is an extra call and some information loss. `SummarizingCompactor` | [Lesson 04](../lessons/04_context_memory/README.en.md) |
| Message Block | 消息块 | An assistant message with tool calls plus all of its tool results. When truncating, keep or drop it as a whole. `split_blocks` | [Lesson 04](../lessons/04_context_memory/README.en.md) |
| Lost in the Middle | 中间遗忘 | A research finding: models use relevant information worst when it sits in the middle of a long context, and best when it's at the beginning or end. | [Lesson 04](../lessons/04_context_memory/README.en.md) |
| Context Rot | 上下文腐烂 | The longer the context, the worse the model uses the information in it. Context is a finite "attention budget". | [Lesson 04](../lessons/04_context_memory/README.en.md) |
| Context Poisoning | 上下文投毒 | A wrong conclusion enters the context and gets cited again and again, compounding the error. | [Lesson 04](../lessons/04_context_memory/README.en.md) |
| Just-in-time Context | 即时上下文 | Instead of preloading everything, keep only "pointers" (file paths, IDs) and load the content with tools when it's needed. | [Lesson 04](../lessons/04_context_memory/README.en.md) |
| RAG (Retrieval-Augmented Generation) | 检索增强生成 | Retrieve relevant material from a knowledge base first, then give it to the model together with the question. Long-term memory is essentially RAG too. | [Lesson 04](../lessons/04_context_memory/README.en.md) · [Lesson 15](../lessons/15_enterprise_rag/README.en.md) |
| Embedding / Vector Search | 嵌入 / 向量检索 | Turning text into a list of numbers (a vector) so that texts with similar meanings get similar vectors, enabling "search by meaning". | [Lesson 01](../lessons/01_llm_essentials/README.en.md) · [Lesson 15](../lessons/15_enterprise_rag/README.en.md) · [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| Hybrid Search | 混合检索 | Using keyword search (e.g., BM25) and vector search together so each covers the other's gaps: the former is good at exact terms, the latter at meaning. | [Lesson 15](../lessons/15_enterprise_rag/README.en.md) · [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| Rerank | 重排序 | After retrieving candidates, reorder them with a finer-grained model so the most relevant ones come first. | [Lesson 15](../lessons/15_enterprise_rag/README.en.md) · [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| Prompt Caching | 提示词缓存 | The model provider caches identical request prefixes, so repeat hits are cheaper and faster. Any change to the prefix invalidates the cache. | [Lesson 14](../lessons/14_cost_latency/README.en.md) |
| Memory Poisoning | 记忆投毒 | Writing malicious or false content into long-term memory so it keeps taking effect in future sessions (e.g., "remember that I'm an admin"). | [Lesson 09](../lessons/09_security/README.en.md) · [Lesson 18](../lessons/18_memory_systems/README.en.md) |
| Right to Erasure | 被遗忘权 | A person's right to have their personal data deleted (a concept from GDPR and similar laws). An agent's memory and logs must be deletable too. `MemoryStore.forget` | [Lesson 04](../lessons/04_context_memory/README.en.md) |

## 4. Agent Architectures, Orchestration, and Multi-Agent Systems

| English | Chinese | In plain words | Lesson |
|---|---|---|---|
| Orchestration | 编排 | The logic that decides who does what and in what order. Code can decide it (a workflow), or the model can (an agent). | [Lesson 06](../lessons/06_orchestration/README.en.md) |
| Prompt Chaining | 提示链 | Splitting a task into fixed steps, where each step's output is the next step's input, with optional gate checks in between. `chain` | [Lesson 06](../lessons/06_orchestration/README.en.md) |
| Routing | 路由 | Classifying the request first, then handing it to a specialized flow (e.g., customer-service triage). `route` | [Lesson 06](../lessons/06_orchestration/README.en.md) |
| Parallelization | 并行化 | Running several model calls at once: either split the task into slices that each handle a part (sectioning), or run the same task several times and vote (voting). `parallel` | [Lesson 06](../lessons/06_orchestration/README.en.md) |
| Majority Vote / Self-Consistency | 多数投票 / 自洽性（自一致性） | Asking the model the same question several times and taking the most common answer to improve reliability (self-consistency was introduced in a 2022 paper by Wang et al.). It is also a form of test-time compute: it only helps on questions the model gets right some of the time; on questions the model simply can't answer, every sample is consistently wrong. `majority_vote` | [Lesson 06](../lessons/06_orchestration/README.en.md) · [Lesson 23](../lessons/23_optimization/README.en.md) |
| Orchestrator-Workers | 编排者-执行者 | One model dynamically breaks down the task, dispatches the pieces to several workers, and combines the results. Unlike parallelization, the subtasks aren't predefined. `orchestrator_workers` | [Lesson 06](../lessons/06_orchestration/README.en.md) |
| Evaluator-Optimizer | 评估-优化 | One model generates and another reviews; revise based on the review until the output passes or the round limit is reached. `evaluator_optimizer` | [Lesson 06](../lessons/06_orchestration/README.en.md) |
| Multi-Agent System | 多 Agent 系统 | Several agents with their own roles (each with its own prompt, tools, and context) collaborate on a task. More capable, but costlier and harder to debug. | [Lesson 06](../lessons/06_orchestration/README.en.md) |
| Agent as Tool / Supervisor | Agent 即工具 / 主管模式 | Wrapping an expert agent as a tool for a supervisor agent. The expert's result goes back to the supervisor, who stays in control of the conversation. `agent_as_tool` | [Lesson 06](../lessons/06_orchestration/README.en.md) · [Lesson 05](../lessons/05_agent_architectures/README.en.md) |
| Handoff | 转交 | The current agent hands the entire conversation to another agent, which takes over the rest of the interaction (control transfers). | [Lesson 06](../lessons/06_orchestration/README.en.md) |
| Reflection | 反思 | Having a model check and critique its own (or another model's) output and improve based on the critique. Reflexion (Shinn et al., 2023) is the representative work. | [Lesson 05](../lessons/05_agent_architectures/README.en.md) · [Lesson 06](../lessons/06_orchestration/README.en.md) · [Lesson 18](../lessons/18_memory_systems/README.en.md) |
| Plan-and-Execute / Plan-then-Execute | 先规划后执行 | Generating a complete plan first and then executing it step by step, replanning when a step fails, instead of deciding one step at a time. More predictable, and also a design pattern for defending against injection (the actions are fixed before any untrusted data is read). | [Lesson 05](../lessons/05_agent_architectures/README.en.md) · [Lesson 09](../lessons/09_security/README.en.md) |
| ReWOO (Reasoning WithOut Observation) | ReWOO | Writing every step's arguments at planning time, with variables that refer to earlier results; execution never goes back to the model, and the answer is written in one go at the end. Few model calls, but no adapting mid-run. | [Lesson 05](../lessons/05_agent_architectures/README.en.md) |
| CodeAct | CodeAct | The model writes a snippet of code that calls tools, loops, and branches; the code's output or error becomes the observation. One step can do a lot, but the code must run in a sandbox. | [Lesson 05](../lessons/05_agent_architectures/README.en.md) |
| Supervisor / Hierarchical | 主管 / 层级 | A supervisor agent delegates subtasks to expert agents, collects the results, and decides the next step itself; with too many experts, supervisors manage supervisors and you get a hierarchy. The supervisor always stays in control. | [Lesson 05](../lessons/05_agent_architectures/README.en.md) |
| Network / Swarm | 网络 / 群体 | No fixed supervisor: any agent can hand the conversation and control off to a better-suited peer, and whoever takes over talks to the user directly. | [Lesson 05](../lessons/05_agent_architectures/README.en.md) |
| Blackboard | 黑板 | Agents don't talk to each other directly; they read and write a shared structured state (the "blackboard"), act when they see something they can handle, and a controller decides who goes next. | [Lesson 05](../lessons/05_agent_architectures/README.en.md) |
| Delegation Contract | 委派契约 | The checklist of what you must give a subagent when delegating a task: the goal, known facts, constraints, and the expected output format. | [Lesson 06](../lessons/06_orchestration/README.en.md) |

## 5. Reliability and Cost

| English | Chinese | In plain words | Lesson |
|---|---|---|---|
| Retryable Error | 可重试错误 | An error that might succeed on retry (429 rate limits, 5xx server errors, timeouts). Retrying a 400 or 401 is pointless. `LLMError.retryable` | [Lesson 08](../lessons/08_reliability/README.en.md) |
| Retry | 重试 | Trying again after a failure: only for retryable errors, at only one layer, and with backoff. `retry_call` | [Lesson 08](../lessons/08_reliability/README.en.md) |
| Exponential Backoff | 指数退避 | The wait before each retry grows exponentially (0.5s, 1s, 2s, ...), giving the downstream service time to recover. `backoff_delay` | [Lesson 08](../lessons/08_reliability/README.en.md) |
| Jitter | 抖动 | Adding randomness to the backoff so thousands of clients don't retry in lockstep. | [Lesson 08](../lessons/08_reliability/README.en.md) |
| Thundering Herd | 惊群效应 | Many clients send requests at the same moment (e.g., all retrying at once) and knock over a service that just recovered. | [Lesson 08](../lessons/08_reliability/README.en.md) |
| Retry Storm | 重试风暴 | Retries multiplied across layers without jitter, amplifying request volume several-fold or even dozens-fold during an outage. | [Lesson 08](../lessons/08_reliability/README.en.md) · [Lesson 27](../lessons/27_durable_workflows/README.en.md) · [Lesson 29](../lessons/29_gateway_and_guardrails/README.en.md) |
| Circuit Breaker | 熔断器 | When a downstream service keeps failing, "trip" and fail fast for a while, then let a few requests through to probe. Three states: closed, open, and half-open. `CircuitBreaker` | [Lesson 08](../lessons/08_reliability/README.en.md) · [Lesson 30](../lessons/30_async_runtime/README.en.md) |
| Fallback / Graceful Degradation | 降级 | When the primary option is unavailable, switch to a backup (fallback model, cache, rules, hand-off to a human). Worse is better than unavailable. `ResilientLLM` | [Lesson 08](../lessons/08_reliability/README.en.md) · [Lesson 29](../lessons/29_gateway_and_guardrails/README.en.md) |
| Checkpoint | 检查点 | Saving the full run state after every step so the run can continue where it left off after a crash or pause. `Checkpointer` | [Lesson 08](../lessons/08_reliability/README.en.md) · [Lesson 26](../lessons/26_state_and_queues/README.en.md) · [Lesson 27](../lessons/27_durable_workflows/README.en.md) |
| Durable Execution | 持久化执行 | An execution model that guarantees a program runs to completion from its last checkpoint even through crashes and restarts. Temporal and LangGraph checkpoints both follow this idea. | [Lesson 08](../lessons/08_reliability/README.en.md) · [Lesson 13](../lessons/13_distributed_concurrency/README.en.md) · [Lesson 27](../lessons/27_durable_workflows/README.en.md) |
| Atomic Write | 原子写入 | A file write either fully succeeds or never happened, so you never end up with a half-written, corrupted file (write to a temp file, then rename it). `FileCheckpointer` | [Lesson 08](../lessons/08_reliability/README.en.md) |
| Saga / Compensation | Saga / 补偿事务 | Splitting a long transaction into steps, each paired with an "undo" action. If it fails midway, the completed steps are undone in turn. | [Lesson 13](../lessons/13_distributed_concurrency/README.en.md) |
| Budget | 预算 | Caps on a run's steps, tokens, dollars, tool calls, and duration. When one is exceeded, the run stops gracefully. `BudgetHook` | [Lesson 08](../lessons/08_reliability/README.en.md) |
| Denial of Wallet | 钱包拒绝服务 | An attacker deliberately makes your agent burn tokens to run up your bill, rather than to take the service down. | [Lesson 08](../lessons/08_reliability/README.en.md) |
| Rainbow Deployment | 彩虹部署 | Several old and new versions run side by side while traffic shifts over gradually, so long-running tasks aren't interrupted by a release. | [Lesson 16](../lessons/16_release_ops/README.en.md) |
| Cost Attribution | 成本归因 | Assigning every cent of model cost to a specific tenant, user, feature, and model. The foundation of FinOps (cloud cost governance) and of pricing. | [Lesson 14](../lessons/14_cost_latency/README.en.md) |

## 6. Security and Governance

| English | Chinese | In plain words | Lesson |
|---|---|---|---|
| Prompt Injection | 提示词注入 | Using text in the input to hijack the model's behavior ("ignore previous instructions..."). Because models can't tell instructions from data, there is no 100% defense today. | [Lesson 09](../lessons/09_security/README.en.md) |
| Indirect Prompt Injection | 间接提示词注入 | The attack instructions aren't typed by the user. They hide in web pages, emails, documents, or tickets the agent reads. More dangerous than direct injection. | [Lesson 09](../lessons/09_security/README.en.md) |
| Jailbreak | 越狱 | Using role-play, encoding, and other tricks to get around a model's safety restrictions. | [Lesson 09](../lessons/09_security/README.en.md) |
| Defense in Depth | 纵深防御 | Stacking multiple layers of protection (input detection, data isolation, least privilege, approval, output filtering, audit), so if one layer is breached, the next one still holds. | [Lesson 09](../lessons/09_security/README.en.md) |
| Spotlighting | 聚光灯（数据标记） | Using tags or encoding to mark external data explicitly as "data, not instructions", helping the model tell sources apart. It lowers the injection success rate but can't eliminate it. `ToolOutputGuard` | [Lesson 09](../lessons/09_security/README.en.md) |
| Lethal Trifecta | 致命三要素 | Coined by Simon Willison: when an agent can access private data, is exposed to untrusted content, and can communicate externally, a single injection is all it takes to exfiltrate data. | [Lesson 09](../lessons/09_security/README.en.md) |
| Data Exfiltration | 数据外泄 | Data quietly sent outside, e.g., through image links in model output or a tool that sends external email. | [Lesson 09](../lessons/09_security/README.en.md) |
| Guardrail | 护栏 | A mechanism that checks and blocks inputs, outputs, or tool calls. It lowers the probability of harm but can't replace permission design. `InputGuard` / `OutputGuard` | [Lesson 09](../lessons/09_security/README.en.md) · [Lesson 29](../lessons/29_gateway_and_guardrails/README.en.md) |
| Least Privilege | 最小权限 | Grant only the minimum permissions the task needs. Assume the model will be fooled, then limit what it can do when it is. | [Lesson 09](../lessons/09_security/README.en.md) |

Good at paraphrases and colloquial questions, but can't tell apart model numbers that differ by one digit, and doesn't understand negation. | [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| Sparse Retrieval / BM25 | 稀疏检索 / BM25 | Scores documents by word overlap with the query through an inverted index, weighting rarer words more. Strongest at exact matches such as model numbers, error codes, and form IDs; returns nothing when the query doesn't use the documents' words. The baseline for almost every retrieval system. | [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| RRF (Reciprocal Rank Fusion) | 倒数排名融合 | Fuses several ranked lists using only ranks, not scores: each list contributes 1 / (k + rank), with k usually 60. Results aren't sensitive to k, so there's almost nothing to tune; it's the default fusion method for hybrid search. | [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| Bi-encoder / Cross-encoder | 双塔 / 交叉编码器 | A bi-encoder encodes the question and each document into one vector separately; document vectors can be computed offline, so it can search the whole corpus. A cross-encoder feeds the question and document through the model together and judges most accurately, but has to run once per pair, so it only reranks the few dozen candidates retrieval returned. | [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| Late Interaction (ColBERT) | 晚交互 | The question and document are still encoded separately, but every token keeps its own vector; at scoring time each question token finds its most similar document token (MaxSim) and the maxima are summed. Close to a cross-encoder in quality, documents can still be precomputed, and the cost is storage. | [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| ANN (Approximate Nearest Neighbor) | 近似最近邻 | Vector indexes that trade a little recall for a lot of speed, such as IVF (buckets) and HNSW (a layered neighbor graph). Defaults can be conservative: pgvector's `ivfflat.probes` defaults to 1, which on Lesson 17's data found fewer than 30% of the true nearest neighbors. | [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| Query Rewriting / HyDE | 查询改写 / HyDE | Rewrite a colloquial question into something that reads more like the documents before searching (e.g., multi-query). HyDE has the model write a hypothetical answer document first and searches with that. The fake document's details are invented: it's bait for retrieval and must never reach the answer. | [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| Recall@k | Recall@k | The share of relevant documents found in the top k results. The metric to watch when choosing context for RAG, because the model can't answer from content that was never retrieved. | [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| MRR (Mean Reciprocal Rank) | MRR | The reciprocal of the rank of the first relevant result (rank 2 gives 1/2), averaged over all queries. The one to watch when users only look at the first result. | [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| nDCG (normalized Discounted Cumulative Gain) | nDCG | Measures the ranking as a whole: more relevant documents should rank higher, the gain at rank i is divided by log2(i+1), and the total is divided by the ideal ranking's score to normalize it to 0–1. Use it when you have graded labels. | [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| Mem0-style Write Path | Mem0 式写入 | "Reconcile" before writing memory: extract facts from the message → fetch the most similar existing memories → have the model choose ADD / UPDATE / DELETE / NOOP → apply rule-based guards (ID checks, single-valued slots, sensitive data) → execute, writing old values to an audit history. From the Mem0 paper (Chhikara et al., 2025). | [Lesson 18](../lessons/18_memory_systems/README.en.md) |
| Tiered Memory (MemGPT / Letta) | 分层记忆 | Treat the context window as RAM and external storage as disk: core memory lives in the prompt, archival memory and the full conversation history live outside, and the agent reads, writes, and pages them in and out with tools. | [Lesson 18](../lessons/18_memory_systems/README.en.md) |
| Memory Consolidation | 记忆巩固 | Merging and summarizing scattered, duplicate memories into fewer, cleaner entries, through merging, reflection, TTL cleanup, and offline tidying during idle time. Derived entries must record their sources so they can be deleted along with them. | [Lesson 18](../lessons/18_memory_systems/README.en.md) |
| Soft Delete / Hard Delete | 软删除 / 物理删除 | A soft delete only marks a memory as no longer valid and keeps the original for audit; use it for "this is out of date." A hard delete actually erases it from storage (together with its history and derived data); use it for "delete my data." | [Lesson 18](../lessons/18_memory_systems/README.en.md) |
| Lineage | 血缘 | Derived data (insights, merged entries, summaries) records which original memories it came from. When an original is deleted, follow the lineage and delete the derived data too; otherwise the deleted information "comes back to life" through it. | [Lesson 18](../lessons/18_memory_systems/README.en.md) |
| Dual-era | 双代兼容 | An implementation that supports both generations of MCP: legacy (2025-11-25 and earlier), which opens a session with an `initialize` handshake, and modern (2026-07-28 onward), which has no handshake and carries the protocol version and client capabilities in every request's `_meta`. | [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |
| Tool Annotations | 工具注解 | Hints in an MCP tool definition that describe its behavior, such as `readOnlyHint` and `destructiveHint`. The spec says annotations from untrusted servers must be treated as untrusted; a tool's risk tier should come from your own review. | [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |
| Rug Pull | 事后变脸 | After a tool passes review, the server quietly changes its definition or behavior in an update. Example: postmark-mcp, an npm package impersonating Postmark, BCC'd every email to the attacker starting with version 1.0.16. The defense is to pin versions and tool-definition fingerprints, and refuse to load and re-review when they change. | [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |
| Process-level Sandbox | 进程级沙箱 | A subprocess + killing the whole process group on timeout + rlimits + a temp directory + a minimal environment. It can control time and resources, but not identity (the code still runs as your user) or the network. | [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |
| OS-level Sandbox / Seatbelt | OS 级沙箱 / Seatbelt | Uses operating-system mechanisms to restrict readable/writable paths and network access by policy, such as macOS Seatbelt (`sandbox-exec`) and Linux bubblewrap / Landlock. Stronger than process-level, but still shares the host kernel. | [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |
| gVisor | gVisor | Implements the Linux system-call interface in user space, so applications in the container never touch the host kernel. Stronger isolation than a plain container, at the cost of higher system-call overhead and slightly worse compatibility. | [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |
| microVM | 微虚拟机 | A lightweight KVM-based virtual machine with its own kernel per sandbox, such as Firecracker (official figures: boots in under 125 ms with under 5 MiB of memory overhead per VM). The isolation level you want when running untrusted code for external users or multiple tenants. | [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |
| Signature / Module / Optimizer (DSPy) | 签名 / 模块 / 优化器 | DSPy's three core ideas: a signature declares "what goes in, what comes out"; a module is a signature plus a calling strategy (Predict, ChainOfThought, ReAct), and modules compose into programs; an optimizer uses training examples and a metric to rewrite instructions and pick examples automatically. | [Lesson 20](../lessons/20_frameworks_bridge/README.en.md) · [Lesson 23](../lessons/23_optimization/README.en.md) |
| StateGraph | StateGraph | A LangGraph graph: a state schema (fields can have reducers, e.g., "append" instead of "overwrite") + node functions + conditional edges. The agent loop is just a back edge, and a checkpoint is saved at every super-step. | [Lesson 20](../lessons/20_frameworks_bridge/README.en.md) |
| interrupt (LangGraph) | interrupt | Calling `interrupt()` inside a node pauses the whole graph; `Command(resume=...)` continues with a resume value. On resume the node **reruns from the top**, so there must be no side effects before `interrupt()`. | [Lesson 20](../lessons/20_frameworks_bridge/README.en.md) |
| Criteria Drift | 标准漂移 | The act of grading outputs changes your idea of what "good" means (Shankar et al., UIST 2024). So write the grading criteria while looking at real outputs, and version both the criteria and the labels. | [Lesson 21](../lessons/21_agent_data/README.en.md) |
| Stratified Sampling | 分层抽样 | Group the data along some dimension (problem signals, tool path, category), then sample each group by quota, so small groups aren't missed. When you compute overall metrics from such a biased sample, reweight by the sampling weights. | [Lesson 21](../lessons/21_agent_data/README.en.md) |
| Synthetic Data | 合成数据 | Test questions or training examples generated by an LLM. Cheap, but with four traps: distribution shift (longer, tidier), self-preference, questions that are too easy, and unreliable expected answers. It can only extend coverage; never use it alone as a test set. | [Lesson 21](../lessons/21_agent_data/README.en.md) |
| Data Leakage | 数据泄漏 | Seeing the exam in advance: data used to improve the system (few-shot examples, failing cases you tuned the prompt against, samples you looked at while revising the rubric) is then used to evaluate it. Splitting data by group and using the test set only once prevents it. | [Lesson 21](../lessons/21_agent_data/README.en.md) · [Lesson 23](../lessons/23_optimization/README.en.md) |
| Train / Dev / Test Split | 训练集 / 开发集 / 测试集 | Train produces examples and feedback; dev is for choosing between options and can be looked at repeatedly; test is evaluated once, at the end. Change the system after looking at test results, and test becomes a second dev set. | [Lesson 21](../lessons/21_agent_data/README.en.md) · [Lesson 23](../lessons/23_optimization/README.en.md) |
| Cohen's kappa | Cohen's kappa | Agreement between two labelers after removing agreement by chance: 1 means perfect agreement, 0 means no better than guessing. With very imbalanced classes, 90% raw agreement can come with a negative kappa (the kappa paradox), so report TPR and TNR as well. | [Lesson 21](../lessons/21_agent_data/README.en.md) |
| Eval Four-tuple | 评估四元组 | The four parts you design or dissect in an agent benchmark: request, environment, stopping criteria, and scorer. Each one changes what you're actually measuring; for example, the scorer should look at the environment's final state, not at what the agent says. | [Lesson 22](../lessons/22_eval_methodology/README.en.md) · [Lesson 24](../lessons/24_coding_agents/README.en.md) |
| Benchmark Validity | benchmark 有效性 | Whether a benchmark's score really measures the ability it claims to, split into two conditions: task validity (capable ⇔ can succeed, with no guessing or loopholes) and outcome validity (the grade really reflects whether the task succeeded). Counterexample: in τ-bench's airline domain, an agent that only returns empty replies scores 38%. | [Lesson 22](../lessons/22_eval_methodology/README.en.md) · [Lesson 25](../lessons/25_proactive_and_frontier/README.en.md) · [Lesson 24](../lessons/24_coding_agents/README.en.md) |
| ABC (Agentic Benchmark Checklist) | ABC 清单 | The checklist Zhu et al. (2025) distilled from flaws in 10 popular agent benchmarks: task validity T.1–T.10, outcome validity O.a–O.i, and reporting R.1–R.13. Examples: clear residual state between runs, keep ground truth out of the agent's reach, and report what a trivial do-nothing agent scores. | [Lesson 22](../lessons/22_eval_methodology/README.en.md) |
| Data Contamination | 数据污染 | Benchmark questions or answers appear in the model's training data, so the score reflects memory rather than ability. Countermeasures: continuously refreshed tasks, private test sets, and human review of the tests. | [Lesson 24](../lessons/24_coding_agents/README.en.md) |
| Pairwise Judge | 成对评委 | The judge compares "is A or B better?" instead of giving each output an absolute score. Good for choosing between models or prompt versions, but it has position bias (in Zheng et al.'s test, GPT-4 kept the same verdict after swapping the order only 65% of the time). The conservative fix: ask in both orders, and count a win only if both verdicts agree; otherwise it's a tie. | [Lesson 22](../lessons/22_eval_methodology/README.en.md) · [Lesson 11](../lessons/11_evals/README.en.md) · [Lesson 17](../lessons/17_retrieval_quality/README.en.md) |
| Confidence Interval | 置信区间 | A range for where the true value probably lies. The 95% Wilson interval for 45/50 is [78.6%, 95.7%], so a difference of two or three cases is very likely just noise. With small samples or rates near 0% / 100%, use the Wilson interval; the textbook Wald interval gives [100%, 100%] for 10/10. | [Lesson 22](../lessons/22_eval_methodology/README.en.md) · [Lesson 11](../lessons/11_evals/README.en.md) · [Lesson 23](../lessons/23_optimization/README.en.md) |
| Paired Test | 配对检验 | Compare two versions task by task on the **same** tasks, which cancels out variance from task difficulty. McNemar's test looks only at tasks where one passed and the other didn't (use the exact binomial test with fewer than 25 of them); a paired bootstrap resamples the per-task differences, and if the interval contains 0, it isn't significant. | [Lesson 22](../lessons/22_eval_methodology/README.en.md) · [Lesson 23](../lessons/23_optimization/README.en.md) |
| Non-inferiority Test | 非劣效检验 | The right way to ask "is the new version at least not worse?": fix in advance the largest regression δ you'll accept, and require the lower bound of the paired difference interval to be > −δ. "Not significantly worse" usually just means the sample was too small. | [Lesson 22](../lessons/22_eval_methodology/README.en.md) |
| Prompt Optimization | 提示词优化 | Let eval scores drive the search: an optimizer reads eval results, proposes new instructions or examples, picks the best on dev, and reports on test exactly once. Representative methods: BootstrapFewShot, OPRO, MIPROv2, GEPA. | [Lesson 23](../lessons/23_optimization/README.en.md) |
| Test-time Compute | 测试时计算 | Spend more compute at inference with the weights unchanged: sample several times and vote, best-of-N with a verifier, or let a reasoning model think longer. Cost is multiplied by N per request, and adding N doesn't help on questions the model simply can't answer (e.g., it doesn't know the company policy). | [Lesson 23](../lessons/23_optimization/README.en.md) |
| Pareto Front | 帕累托前沿 | The set of candidates not dominated by any other (A dominates B if it's no worse on every sample and strictly better on at least one). GEPA uses it to keep prompts that are each good at something, so the search doesn't get stuck in a local optimum. | [Lesson 23](../lessons/23_optimization/README.en.md) |
| Winner's Curse | 赢家诅咒 | When you pick the candidate with the highest dev score, you tend to pick the one whose noise happened to be positive, so its dev score is inflated. More candidates and a smaller dev set make it worse. Use dev scores to choose, never to report. | [Lesson 23](../lessons/23_optimization/README.en.md) |
| Distillation | 蒸馏 | Run a large model (or a large model + a good prompt) on many inputs, keep the trajectories a verifier marks correct, and use them to fine-tune a small model. It's the same thing as BootstrapFewShot in a different place: one writes the trajectories into weights, the other into the prompt. | [Lesson 23](../lessons/23_optimization/README.en.md) |
| LoRA (Low-Rank Adaptation) | LoRA | Freeze the original weights and learn only a low-rank "correction" ΔW = BA. The paper reports 10,000× fewer trainable parameters and 3× less GPU memory than full fine-tuning of GPT-3 175B; after training, the correction can be merged back, adding no inference latency. | [Lesson 23](../lessons/23_optimization/README.en.md) |
| DPO (Direct Preference Optimization) | DPO | Preference optimization trained directly on "better / worse" answer pairs, skipping RLHF's separate reward model and reinforcement-learning sampling. | [Lesson 23](../lessons/23_optimization/README.en.md) |
| Reward Hacking / Specification Gaming | 钻评分器空子 | Meeting the letter of the grading rule without achieving the real goal: a coding agent edits the tests or special-cases the test inputs; an optimizer that targets an LLM judge learns to please the judge. | [Lesson 23](../lessons/23_optimization/README.en.md) · [Lesson 24](../lessons/24_coding_agents/README.en.md) |
| Harness | harness | The layer of code around an agent that decides what it sees each time, what it can do, how its work is accepted, and how to pick up after an interruption. A long-running harness uses a feature list + a progress file + git so that each fresh, memoryless session can take over. | [Lesson 24](../lessons/24_coding_agents/README.en.md) |
| FAIL_TO_PASS / PASS_TO_PASS | FAIL_TO_PASS / PASS_TO_PASS | SWE-bench's two groups of hidden tests: those that fail before the fix and must pass after it ("did you fix it?"), and those that must pass both before and after ("did you break anything else?"). A task counts as resolved only if both groups pass completely. | [Lesson 24](../lessons/24_coding_agents/README.en.md) |
| Proactive Agent | 主动式 Agent | An agent that finds needs on its own and decides whether to speak up, without waiting for the user to ask. The hard part isn't "figuring out what you need" but "knowing when to stay quiet." | [Lesson 25](../lessons/25_proactive_and_frontier/README.en.md) |
| Mixed-initiative | 混合主动 | Both the person and the agent can initiate actions, and whoever is better placed takes the lead. From Horvitz's 12 principles (1999); the core idea is to decide by expected utility across benefit, cost, and uncertainty. | [Lesson 25](../lessons/25_proactive_and_frontier/README.en.md) |
| User Model | 用户模型 | The agent's set of inferences about "what this person is like and what they want," each with a confidence and evidence, which the user can view, correct, and delete. Memory stores "what happened"; a user model stores "so I infer that you…". | [Lesson 25](../lessons/25_proactive_and_frontier/README.en.md) · [Lesson 18](../lessons/18_memory_systems/README.en.md) |
| Interruption Cost | 打扰成本 | Every time the agent speaks up unprompted, it takes the user's attention, and the cost is higher during focus time, meetings, or late at night. A decider speaks only when "benefit × confidence − context cost" clears a threshold; otherwise it holds the item for a digest or drops it. | [Lesson 25](../lessons/25_proactive_and_frontier/README.en.md) |
| 50% Time Horizon | 50% 时间跨度 | METR's metric: the length of task (measured by how long it takes a human) that an AI can complete with a 50% success rate. The paper found it has doubled roughly every 7 months since 2019. Note that it's defined at 50% success, which is not the same as reliable. | [Lesson 25](../lessons/25_proactive_and_frontier/README.en.md) |

The Google SRE Workbook recommends multiwindow, multi-burn-rate alerts: page when both the 1-hour and 5-minute burn rates exceed 14.4, or both the 6-hour and 30-minute rates exceed 6; open a ticket when both the 3-day and 6-hour rates exceed 1. | [Lesson 28](../lessons/28_production_observability/README.en.md) |
| Virtual Key | 虚拟 key | A stand-in key the model gateway issues to each team or service. Services hold only this key, and the real provider keys stay inside the gateway. Each virtual key or team can have its own budget and rpm / tpm limits, and a leaked key can be revoked on its own. | [Lesson 29](../lessons/29_gateway_and_guardrails/README.en.md) |
| Policy as Code | 策略即代码 | Writing authorization rules as a separate policy file instead of if-else scattered through the code. It's reviewable (the security team reads the diff), testable (schema validation plus decision test cases), auditable (every decision names the policy behind it), and released independently of the code. `CedarPolicy` | [Lesson 29](../lessons/29_gateway_and_guardrails/README.en.md) |
| Cedar | Cedar | An authorization policy language: permit / forbid plus `when` / `unless`. Any matching forbid denies; otherwise a matching permit allows; if nothing matches, the default is deny. Policies can be validated statically against a schema. Watch out: a policy that errors during evaluation is **skipped**, so the adapter has to treat evaluation errors as a deny. | [Lesson 29](../lessons/29_gateway_and_guardrails/README.en.md) |
| ABAC / ReBAC | ABAC / ReBAC | Two kinds of authorization finer-grained than RBAC. ABAC decides by attributes and arguments ("you can only reset your own password," "free-plan tenants can't run dangerous operations"). ReBAC decides by relationships ("the document belongs to a folder, and the folder is shared with a team"); it traces back to Google's Zanzibar, and OpenFGA is an open-source implementation. | [Lesson 29](../lessons/29_gateway_and_guardrails/README.en.md) |
| Fail-closed / Fail-open | 失败即关闭 / 失败即放行 | Whether a control component (authorization, rate limiting, a guardrail) denies everything or allows everything when it fails itself. Security boundaries must fail closed (Cedar evaluation errors count as a deny; an approval that times out is rejected). A detection layer may fail open to stay available, but it must record the failure and alert. | [Lesson 29](../lessons/29_gateway_and_guardrails/README.en.md) · [Lesson 27](../lessons/27_durable_workflows/README.en.md) |
| Classifier Cascade | 级联分类器 | Guardrails in tiers: a cheap classifier (regex, a small model) decides first and allows or blocks when it's confident; only uncertain cases go to an expensive one (an LLM judge, a managed service). Most traffic ends at the first tier, and the thresholds decide which kind of first-tier mistake you inherit. `CascadeClassifier` | [Lesson 29](../lessons/29_gateway_and_guardrails/README.en.md) |
| Little's Law | 利特尔法则 | L = λ × W: the number of requests in the system at once equals the arrival rate times the average time each one stays. At 50 requests per second and 8 seconds each, you must be able to have 400 sessions "waiting" at once. For capacity planning, take W at p95, not the average. | [Lesson 30](../lessons/30_async_runtime/README.en.md) |
| Bulkhead | 舱壁 | Like the partitions between a ship's compartments: cap how many runs each tenant can have in flight, plus a global cap, so a tenant that fills its own slots doesn't take anyone else's. The price is that it isn't work-conserving: a noisy tenant can't use slots others leave empty. `KeyedLimiter` | [Lesson 30](../lessons/30_async_runtime/README.en.md) |
| Structured Concurrency | 结构化并发 | Child tasks can't outlive the scope that created them: the scope waits for all of them before exiting, and if one fails, it cancels the rest and waits for them to clean up (Trio's nursery, asyncio's `TaskGroup`). A stray `create_task` is like a goto: nobody learns that it failed, and nobody waits for it to clean up after a cancellation. | [Lesson 30](../lessons/30_async_runtime/README.en.md) |
| Cancellation Propagation | 取消传播 | Carrying the caller's cancellation (client disconnect, timeout, shutdown) all the way to the in-flight model call and tools, so they actually stop and stop costing money. After cleaning up, `CancelledError` must be re-raised. In frameworks with level-triggered cancellation such as AnyIO, `await`s during cleanup need a shield. | [Lesson 30](../lessons/30_async_runtime/README.en.md) |
| Hard Timeout / Process Isolation | 硬超时 / 进程隔离 | Python threads can't be killed, and coroutines can only be cancelled at an `await`, so an infinite loop with no `await` only stops when you kill its process. `isolated(tool)` runs a tool in a subprocess and kills it on timeout. It isn't a sandbox: untrusted code still belongs in a container or microVM. | [Lesson 30](../lessons/30_async_runtime/README.en.md) · [Lesson 19](../lessons/19_mcp_and_sandbox/README.en.md) |
| Liveness / Readiness Probe | 存活探针 / 就绪探针 | Kubernetes's two health checks. A failed liveness probe restarts the container, so it should only check that this process can still respond. A failed readiness probe takes the Pod out of traffic without restarting it, so it's the place to check dependencies and "shutting down." Lesson 31's reference service keeps the database out of its liveness probe; otherwise a database blip would restart every Pod at once. | [Lesson 31](../lessons/31_deployment_and_scaling/README.en.md) |
| Graceful Shutdown | 优雅停机 | After SIGTERM: fail the readiness probe and stop accepting requests and claiming tasks → let in-flight tasks finish within the grace period → cancel the ones that can't and hand them back to the queue → flush traces, close connection pools, and exit. All of it has to fit within `terminationGracePeriodSeconds` (30 seconds by default, and time spent in preStop counts). `stop_on_signals` | [Lesson 31](../lessons/31_deployment_and_scaling/README.en.md) · [Lesson 26](../lessons/26_state_and_queues/README.en.md) |
| Queue-depth Autoscaling | 按队列积压扩缩容 | Adding and removing workers based on how many tasks are queued and how long the oldest one has waited, not on CPU: agent workers spend most of their time waiting on the model, so CPU barely moves. KEDA's `postgresql` scaler can scale directly on the result of a SQL query. Set the replica ceiling from your model quota. | [Lesson 31](../lessons/31_deployment_and_scaling/README.en.md) · [Lesson 26](../lessons/26_state_and_queues/README.en.md) |
| Coordinated Omission | 协调遗漏 | A closed-loop load test (each virtual user waits for its previous request before sending the next) slows down along with the system, so it misses the slowest stretch and flatters the latency distribution. To measure tail latency at a fixed arrival rate, use an open-loop test, such as k6's arrival-rate executors or wrk2. | [Lesson 31](../lessons/31_deployment_and_scaling/README.en.md) |

## Appendix: Commonly Confused Pairs

| Pair | Difference |
|---|---|
| Workflow vs. agent | The flow is decided by code vs. by the model. |
| Agent as tool vs. handoff | The result goes back to the caller, who stays in control vs. control transfers entirely to the other agent. |
| Short-term memory vs. long-term memory | The current session's message history vs. external storage that persists across sessions. |
| Sliding window vs. compaction | Drop old messages outright vs. summarize them. |
| Guardrail vs. permission | Detect and block suspicious content (lowers the probability) vs. limit what can be done (limits the consequences). |
| Direct injection vs. indirect injection | The attack comes from user input vs. hides in external content the agent reads. |
| Audit log vs. debug log | For compliance: complete, tamper-proof, never sampled vs. for engineers: can be sampled and discarded. |
| pass@k vs. pass^k | At least one success vs. success every time. |
| Retry vs. fallback | Try the same approach again vs. switch to a backup option. |
| Checkpoint vs. session history | The full state of a half-finished run (lets you resume execution) vs. the conversation record (lets you keep chatting). |
| Rate limit vs. quota | A cap on rate per unit of time vs. a cap on total usage per period. |
| MCP vs. A2A | Connects agents to tools and data sources vs. connects agents to other agents. |
| At-least-once vs. exactly-once | May duplicate but never loses vs. takes effect only once (in practice, achieved with "at-least-once + idempotency"). |
| Distributed lock vs. optimistic concurrency vs. per-session partitioning | Grab the lock, then write vs. check for version conflicts at write time vs. make concurrent messages for the same session impossible in the first place. |
| Pre-filtering vs. post-filtering | Scope by permission at retrieval time vs. drop results afterward (prone to leaks or poor recall). |
| Shadow mode vs. canary vs. A/B | Validates correctness (invisible to users) vs. validates stability (a small slice of real traffic) vs. validates business impact (group comparison). |
| Exact-match cache vs. semantic cache vs. prompt cache | Hits only on identical input vs. hits on similar meaning vs. the provider reuses computation for identical prefixes. |
| Dense retrieval vs. sparse retrieval | Search by meaning (good at paraphrases, can't tell apart model numbers one digit apart) vs. search by words (good at exact matches, returns nothing when the vocabulary doesn't match). |
| Retrieval vs. reranking | Quickly pull dozens to hundreds of candidates from the whole corpus, aiming "not to miss" vs. compare only those candidates carefully, aiming "to order them right." Reranking can't recover what retrieval missed. |
| Write-time vs. read-time reconciliation | Decide add / update / delete when writing memory, so reads return the current state vs. keep the full dated history and let a strong model sort out contradictions at read time. |
| Protocol error vs. tool execution error | The request itself is wrong (unknown method, unknown tool): return a JSON-RPC error vs. the request is valid but the tool didn't succeed (including invalid argument values): return `isError: true` so the model can fix it. |
| Dev set vs. test set | Look at it as often as you like and use it to choose candidates vs. evaluate once at the end and use it to report. Change the system after looking at test, and test is no longer trustworthy. |
| Prompt optimization vs. test-time compute vs. fine-tuning | A one-time investment in text you can roll back anytime vs. every request's cost multiplied by N vs. changing weights, which needs data and training, and rolling back means managing model versions yourself. |
| Checkpoint vs. harness | Saves the "brain state" so the same conversation resumes where it stopped vs. saves the "work itself" (feature list, progress file, git) so a brand-new session takes over by reading the handover notes. |
| Agent harness vs. evaluation harness | The system that lets a model act as an agent (processes inputs, orchestrates tool calls) vs. the infrastructure that runs evals end to end (provides tasks and tools, runs them concurrently, records every step, grades, aggregates). |
| Pointwise grading vs. pairwise comparison | Score or pass/fail each answer on its own, good for regression tests and release gates vs. ask which of two answers is better, more sensitive and good for choosing models or prompts, but prone to position bias. |
| Event-driven agent vs. proactive agent | An architecture question: how events come in, get queued, and stay idempotent vs. an interaction question: after handling an event, whether to interrupt the person, when, and with what. |
| Plain CAS vs. fenced takeover | Never loses an update, but when a zombie and a new worker read the same version, the first writer wins, which may be the zombie vs. the newest lease holder voids the old version number the moment it reads, so the new holder always wins. |
| Checkpoint + lease queue vs. Temporal | You write the recovery trigger, mutual exclusion, and approval timers yourself, with only Postgres added vs. the service records the event history, dispatches recovery, and owns the timers, at the cost of running another service and accepting determinism constraints. |
| Signal vs. update | Fire and forget; the sender doesn't know whether the workflow accepted it vs. waits for the workflow to handle it and returns a result, and a validator can reject it before it's written to the history. |
| Head sampling vs. tail sampling | Decided when the request starts, cheap for the SDK but drops error traces in proportion vs. decided once the whole trace has arrived, keeping every error and slow request, at the cost of memory and routing by trace ID to one Collector. |
| Bulkhead vs. rate limit | Caps how many run at the same time (concurrency) vs. caps how many happen per unit of time (rate). |
| Liveness probe vs. readiness probe | Failure restarts the container, so it checks only this process vs. failure removes the Pod from traffic without a restart, so it can check dependencies. |
| Fail-closed vs. fail-open | When the component fails, deny everything to stay safe vs. allow everything to stay available. Authorization and approval take the former; a detection layer may take the latter, but it must record and alert. |
